围绕 `HEAD` 与用户指定的固定参考点之间的 diff 展开双维度审查：

- **规范 (Standards)**：代码是否符合本仓库记录的编码规范？
- **需求规格 (Spec)**：代码是否忠实实现了初始 issue / spec 的要求？

两个维度分别作为**并行子 Agent (parallel sub-agents)** 独立运行，避免彼此上下文污染，随后由本 skill 汇总结果。

Issue 跟踪器说明应已提供。如果缺少 `docs/agents/issue-tracker.md`，提示用户运行 `/setup-matt-pocock-skills`。

## 执行流程

### 1. 锚定固定参考点 (Pin the fixed point)

获取用户指定的固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。若用户未指定，主动询问。

生成并捕获一次 diff 命令：`git diff <fixed-point>...HEAD`（使用三点语法 `...`，与 merge-base 进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在执行后续步骤前，确认固定点有效（`git rev-parse <fixed-point>`）且 diff 非空。若引用无效或 diff 为空，在此处直接报错终止，不进入后续并行子 Agent 执行。

### 2. 确定需求规格来源 (Identify the spec source)

按以下优先级寻找初始 spec：

1. commit message 中的 issue 引用（如 `#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的流程拉取。
2. 用户作为参数传入的文件路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 spec 文件。
4. 若均未找到，询问用户 spec 的位置。若用户确认无 spec，**Spec** 子 Agent 跳过执行并在报告中注明“无可用需求规格 (no spec available)”。

### 3. 确定规范来源 (Identify the standards sources)

检索仓库中记录代码编写规范的文件，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库自身文档外，规范维度始终携带以下**代码异味基线 (smell baseline)**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），在仓库无任何文档时同样适用。受以下两条规则约束：

- **仓库文档优先**：仓库记录的规范具有最高优先级；若仓库规范明确允许某种 baseline 标记的写法，压制该代码异味。
- **始终基于主观判断**：每项坏味道均为启发式标注（如“疑似特性依恋”），属于建议性质。跳过静态工具（linter 等）已强制校验的内容。

各项坏味道的定义（*是什么* → *如何修复*），与 diff 进行对照：

- **神秘命名 (Mysterious Name)**：函数、变量或类型的名称未能清晰表达其职责或存储内容。→ 重命名；若想不出恰当名称，说明设计本身不清晰。
- **重复代码 (Duplicated Code)**：相同的逻辑结构出现在本次变更的多个代码块或文件中。→ 提取公共逻辑，两处均改为调用该逻辑。
- **特性依恋 (Feature Envy)**：某个方法访问另一个对象的数据多于自身的数据。→ 将该方法移至所依恋的数据所在对象中。
- **数据泥团 (Data Clumps)**：相同的几个字段或参数总是一起出现（意味着该封装独立类型了）。→ 将它们打包为一个独立的结构或类传递。
- **基本类型偏执 (Primitive Obsession)**：使用基本类型或字符串代替应有独立业务含义的领域概念。→ 为该概念定义轻量级专用类型。
- **重复的 Switch 语句 (Repeated Switches)**：针对同一类型的 `switch`/`if` 分支级联结构在变更中多处重复出现。→ 改用多态，或两处共享映射表。
- **散弹式修改 (Shotgun Surgery)**：一处逻辑改动导致 diff 中零散修改大量不同文件。→ 将紧密变更的代码收拢至同一个模块中。
- **发散式变化 (Divergent Change)**：同一个文件或模块因多种不同原因频繁修改。→ 按变更原因拆分为独立模块。
- **夸夸其谈未来性 (Speculative Generality)**：为了 spec 中未要求的未来需求添加了抽象、参数或钩子。→ 删除多余设计，直接内联回退，直到真正有需求时再引入。
- **过长消息链 (Message Chains)**：形如 `a.b().c().d()` 的长调用链，使调用方产生了不应有的深层依赖。→ 在首个对象上封装方法隐藏调用链。
- **中间人 (Middle Man)**：某个类或函数绝大多数代码仅在把调用向下委托。→ 移除该中间层，直接调用目标对象。
- **被拒绝的遗赠 (Refused Bequest)**：子类或实现类忽略或重写了继承来的绝大部分行为。→ 放弃继承，改用组合。

### 4. 并行启动两个子 Agent (Spawn both sub-agents in parallel)

**规范子 Agent (Standards sub-agent) Prompt** 应包含：

- 完整的 diff 命令与 commit 列表。
- 步骤 3 中找到的规范文件列表，**外加步骤 3 的代码异味基线全文**（子 Agent 无法通过其他途径获取该基线）。
- 任务说明：“针对 diff 涉及的各文件/代码块，逐一报告：(a) 违反仓库既有规范之处：注明规范出处（文件 + 对应规则）；(b) 发现的 baseline 代码异味：指出具体坏味道并引用对应代码块。明确区分强制规范与主观启发式建议：仓库规范可作为强制项，baseline 坏味道始终为主观判断，且仓库规范优先于 baseline。跳过静态工具已检查的项。字数控制在 400 词以内。”

**需求规格子 Agent (Spec sub-agent) Prompt** 应包含：

- diff 命令与 commit 列表。
- spec 路径或已拉取的 spec 全文内容。
- 任务说明：“报告：(a) spec 要求但缺失或仅部分实现的需求；(b) diff 中超出 spec 范围的额外行为（范围蔓延）；(c) 虽已实现但实现逻辑存在缺陷的需求。每项问题均需引用 spec 对应原文行。字数控制在 400 词以内。”

若缺少 spec，跳过 Spec 子 Agent，并在最终报告中注明。

### 5. 汇总结果 (Aggregate)

在 `## 规范 (Standards)` 与 `## 需求规格 (Spec)` 两个独立标题下展示报告，保持原文或仅做轻微整理。不合并或交叉重排两边的结论，维持两个维度的评估相互独立（详见*为何拆分双维度*）。

报告末尾输出单行摘要：各维度的发现总数，以及*各维度内部*最严重的问题（若存在）。不跨维度评选单一最严重问题，防止破坏维度的独立隔离。

## 为何拆分双维度 (Why two axes)

代码变更可能在一个维度达标而在另一个维度不及格：

- 代码完全符合规范，但实现的需求完全跑偏 → **规范通过，需求规格失败。**
- 代码严格实现了 issue 要求的逻辑，但严重破坏了项目的架构规范与命名约定 → **需求规格通过，规范失败。**

独立呈现两个维度的报告，防止单个维度的结果掩盖另一个维度的问题。
